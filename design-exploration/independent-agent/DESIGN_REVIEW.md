# 独立 iOS 设计评审

## 1. 我从文档推导出的产品骨架

我把这个产品理解为“家庭状态 → 发现问题 → 直接处理 → 结果回到家庭系统”的共享中控，而不是五个并列工具。

一级导航保留五个家庭入口：总览、日历、信箱、设备、我们。它们是 wayfinding，不是五套互不相干的视觉世界。总览是产品锚点，负责在几秒内回答“家里是否正常、我需要做什么、今天和最近发生了什么”；设备、信箱和写信流程是从总览延伸出来的处理路径。

我在探索图里把物理系统的链路显式化：Mac mini 是家庭服务协调者，ESP32 是硬件连接上下文，打印机、E-ink 和 UPS 是可观察、可操作的实体节点。信箱则承担持久事件记录，既包含系统通知和设备事件，也包含打印信件与打印任务。

## 2. 关键设计判断

### 家庭状态是第一信息层

健康态总览保持安静：标题和“正常”先回答状态，日程、待办、未读信箱和设备连接作为下一层摘要。异常态没有改变整套 UI，只把“需要你处理”提升到标题之后，并给出“查看详情 / 稍后处理”这类直接动作。这体现了文档里“严重家庭安全问题 → 设备异常 → 今日安排 → 信箱 → 最近发生”的动态优先级。

### 统一状态语言跨越生活与硬件

“已连接 / 连接问题 / 待确认 / 已处理 / 排队中 / 打印完成”同时出现在总览、信箱和设备中心。这样用户不会把设备中心理解成另一个后台系统，也能从事件回到具体设备。

### 纸张是实体输出的证据，不是整套界面的皮肤

纸张材质只出现在信件和 E-ink 预览中；列表、导航、按钮和设备层级仍然遵循 iOS 原生节奏。Ghost 出现在状态或信件语境里，用来建立家庭品牌识别，但不会代替错误说明、状态文本或下一步动作。

### 信箱是事件档案，不是“信件收件箱”

信箱画面把系统消息、设备恢复、打印信件和打印任务放在同一条持久时间线里，用分类筛选降低认知负担。打印信件是其中一个类别，不会吞掉设备事件和 Agent 处理记录的空间。

### 聚焦任务用原生任务层级承载

写信 / 打印预览采用聚焦任务屏的方向：顶部是取消和下一步，中间是有实体感的纸张预览，底部是纸张样式、附加内容和确认打印。实现时应落到 `NavigationStack + Sheet` 或等价的原生编辑层级，而不是复刻一个网页画布。

## 3. 关键假设（仅用于视觉探索）

- 假设需要用一个“ESP32 连接问题”示例展示高优先级设备异常如何上浮；这不是对真实心跳字段、故障原因或通知阈值的断言。
- 假设设备中心需要一条简短的家庭设备摘要，以及 Mac mini、ESP32、打印机、E-ink、UPS 五个清晰层级；具体可用操作仍由后端和固件能力决定。
- 假设 `revision` 可以作为 E-ink 发布后的技术标识示例；正式字段名、语义和生命周期需要以后端契约确认。
- 假设写信流程需要在确认打印前同时看见信件内容、纸张与样式、附加内容和即将进入队列的结果；具体表单字段没有在文档中完全定义。
- 画面里的时间、未读数、队列状态、设备状态和文案都是 illustrative data，不能直接转成种子数据或产品承诺。

## 4. 文档中的歧义 / 需要确认

- 第一版到底有哪些环境与安全传感器、真实读数和阈值；当前探索没有绘制任何传感器数值，以免越过文档边界。
- 哪些安全事件需要系统 Push / Banner 打断，哪些只进入信箱；“安全问题”与“设备异常”的通知策略仍未定。
- Mac mini、ESP32、打印机、E-ink、UPS 各自真正支持哪些操作，尤其是重启、重试、刷新和发布动作。
- Mac mini 服务身份验证、HTTPS、公网或 Tailscale 访问方式，以及离线缓存能显示到什么程度。
- Agent 只能只读分析、提出建议，还是可以执行设备操作；这会改变信箱行内动作、确认提示和权限文案。
- 写信的纸张、样式、附加内容和打印队列的真实模型尚未完全定义。
- 是否支持 iPad 横屏，以及 iPhone 动态字体放大后的密度取舍。

## 5. 这是否真的体现了“家庭中控中心”

是，至少在产品概念层面体现了三个关键连接：

1. 总览把日常安排、待办、信箱和设备健康放在同一家庭状态模型中。
2. 设备中心明确展示从 Mac mini / ESP32 到打印机、E-ink、UPS 的实体链路，而不是孤立的智能家居卡片。
3. 写信和打印预览把数字信息变成物理家庭输出，且完成结果可以回到信箱与总览。

仍然需要在工程实现中验证的一点是“行动闭环”：每一个异常或任务都应能从总览 / 信箱进入详情、完成可用动作，并把成功或失败记录回家庭事件流。如果实现只停留在静态状态展示，它就会退化成 dashboard，而不是文档要求的家庭控制中心。

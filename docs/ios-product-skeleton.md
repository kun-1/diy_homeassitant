# 原生 iOS 产品骨架与页面结构

状态：访谈确认版 0.1  
日期：2026-09-18

## 1. 产品一句话

这是一个面向家庭共享使用的、可持续扩展的 Home Assistant 中控中心：它把家庭日常、日历、待办、打印信件、E-ink 内容和家中硬件状态组织在同一个系统里，让家人能够快速理解家庭状态、发现问题并直接处理。

## 2. 核心产品模型

```text
家庭总览
  ↓
发现问题、任务或新事件
  ↓
进入对应模块
  ↓
直接编辑、控制、打印或交给 Agent
  ↓
结果回到总览与信箱
```

App 不应该被理解成五个平行的网页页面，而应该被理解成一个家庭系统。一级导航只是让用户找到不同类型的内容，所有页面共享同一套状态语言、视觉层级和反馈方式。

## 3. 第一版范围

第一版完整承接当前 PWA 已完成的功能：

- 家庭今日总览
- 日历查看与编辑
- 待办查看、创建、完成和管理
- 纪念日、倒数日和共同愿望
- 写信、信件样式、附加内容、打印预览和打印队列
- 统一信箱，包括信件、系统消息、设备事件和打印事件
- Mac mini、ESP32、打印机、E-ink、UPS 的状态查看
- 设备详情、支持的操作和重启
- E-ink 显示模式、内容选择和预览
- 离线/连接失败/设备异常/打印失败等反馈

## 4. 未来扩展

这些能力暂不作为第一版的核心实现，但信息架构需要为它们预留位置：

- 卧室空气质量：温度、湿度、CO₂、颗粒物等
- 厨房空气与安全：燃气或有毒气体检测
- 更多家庭环境传感器
- 摄像头或其他家庭监控
- Agent 自动阅读信箱事件、判断问题并提出或执行处理动作
- 更丰富的家庭自动化和跨设备联动

未来扩展的共同入口是“家庭总览 → 事件/设备详情”，不为每一种传感器建立孤立的子产品。

## 5. 一级信息架构

建议原生 iOS 使用标准 TabView，保留清晰的五个一级区域，但让它们共享同一个家庭系统外壳：

```text
总览
├── 家庭健康状态
├── 今日安排
├── 待办
├── 未读信箱摘要
├── 最近发生
├── 当前 E-ink 内容
└── 环境摘要

日历
├── 月视图
├── 周视图
├── 日期详情
└── 新增/编辑日程

信箱
├── 全部
├── 系统通知
├── 设备事件
├── 打印信件
├── 打印任务
├── Agent 处理记录
└── 归档/已处理

设备
├── 家庭设备总览
├── Mac mini
├── ESP32
├── 打印机
├── E-ink
├── UPS
├── E-ink 内容编排
└── 操作与重启

我们
├── 在一起的天数
├── 纪念日/倒数日
├── 共同完成
└── 心愿清单
```

应用设置不是一个与上述区域平行的“网页”，而是通过 toolbar、设备设置或系统设置入口进入。

## 6. 家庭总览页面

### 6.1 页面任务

用户打开 App 后，在几秒内回答三个问题：

1. 家里现在是否健康、正常？
2. 有没有需要我处理的问题？
3. 今天和最近发生了什么？

### 6.2 动态优先级

固定的信息类型不代表固定的视觉顺序。总览根据严重性和相关性动态组织内容：

```text
严重家庭安全问题
→ 设备异常
→ 今日安排与待办
→ 未读信箱
→ 最近事件
→ 当前 E-ink 内容
→ 环境数据详情
```

在家庭健康时，页面应该安静、清晰、可快速浏览；当出现严重问题时，问题卡片移动到最上方，并提供直接进入详情和处理的动作。

### 6.3 建议的首屏结构

```text
大标题：家庭现在怎么样？
家庭健康状态摘要
  ├── 正常 / 有事项 / 需要立即处理
  └── 最近更新时间

需要你处理
  └── 动态显示最高优先级事件或设备问题

今天
  ├── 下一项日程
  ├── 今日待办进度
  └── 未读信箱数量

最近发生
当前 E-ink 内容 / 环境摘要
```

这不是要求首屏永远展示所有模块，而是规定信息从“家庭状态”向“具体内容”逐步展开。

## 7. 信箱与通知

### 7.1 两者的区别

```text
通知
短暂、即时、用于提醒用户注意
可能表现为 iOS Push、Banner 或短暂 Toast
不承担完整历史记录

信箱
持久、可阅读、可分类、可归档、可交给 Agent
是家庭事件的可追溯记录
```

### 7.2 信箱分类

- 系统消息
- 设备异常
- 设备恢复
- 打印任务
- 打印信件
- 环境与安全事件
- Agent 处理记录

每一项都应该有时间、来源、状态、严重性和下一步动作。安全相关事件不能只用颜色表达。

## 8. 关键任务流程

### 8.1 写信并打印

```text
信箱/信件 → 写信 → 输入内容 → 选择纸张和附加内容
→ 实时预览 → 确认打印 → 加入打印队列
→ 打印完成/失败事件回到信箱
```

写信是一个聚焦任务，适合使用 NavigationStack + Sheet/全屏编辑体验，不应把所有选项塞进一张长网页。

### 8.2 设备异常处理

```text
总览出现异常 → 进入设备或事件详情
→ 查看原因、最近心跳和可用操作
→ 重试、重启、确认已处理或交给 Agent
→ 结果生成恢复/失败事件
```

### 8.3 E-ink 内容更新

```text
设备 → E-ink → 选择显示模式与内容
→ 查看真实比例预览 → 保存/发布
→ 显示 revision 和更新时间
→ ESP32 刷新结果回到事件记录
```

### 8.4 日历与待办

日历、待办和共同事项均应支持直接创建、编辑和完成。总览只呈现与今天相关的摘要，完整管理在对应模块中完成。

## 9. 状态设计

每个核心模块至少需要明确以下状态：

- 首次加载
- 已加载且正常
- 空状态
- 离线但有缓存
- 正在同步
- 同步失败
- 设备异常
- 操作成功
- 操作失败且可重试
- 操作失败但需要人工处理

总览不应该把所有状态都变成弹窗。能被信箱记录的事件优先进入信箱；真正需要立即打断用户的安全问题才使用系统通知或高优先级提示。

## 10. 原生 iOS 交互原则

- 使用标准 TabView 作为一级导航，但不要让每个 Tab 变成独立网页。
- 使用 NavigationStack 表达“总览 → 详情 → 编辑”的层级。
- 使用 Sheet 表达写信、E-ink 编排、设备操作等聚焦任务。
- 保留系统边缘返回手势。
- 使用 SwiftUI 原生控件、SF Symbols、Dynamic Type、Dark Mode 和 Reduce Motion。
- 所有可点击控件至少 44pt。
- Ghost 和手绘元素只能增强理解，不能替代文字标签、错误说明或状态信息。

## 11. 设计方向

### 方向名称

**一间会呼吸的家庭控制室**

### 要保留的品牌资产

- 温暖的家庭氛围
- Ghost 作为家庭助手和状态角色
- 纸张、手写、信件和打印物的实体感
- 当前柔和的纸张、墨色、珊瑚、鼠尾草和琥珀色倾向

### 要改变的结构问题

- 去掉 PWA 的假手机边框和浏览器压缩感。
- 不再让每个 Tab 拥有一套互不相干的网页布局。
- 统一状态卡片、标题、间距、反馈和动作语言。
- 让家庭健康状态成为视觉锚点，让 Ghost 和纸张成为品牌点缀。
- 让设备控制和日常生活都回到同一个家庭模型中。

### 视觉判断标准

一个页面即使没有 Ghost 和插画，也应该能让人理解家庭当前状态；加入 Ghost 和纸张以后，应该更像“这个家庭的系统”，而不是更像一张装饰海报。

## 12. 尚未决定但不阻塞骨架的问题

- 第一版具体支持哪些空气质量传感器和读数。
- 各类安全事件的真实阈值和通知策略。
- 是否支持 iPad 横屏布局。
- Mac mini 服务的正式身份验证、HTTPS 和公网访问方式。
- Agent 的具体权限：只读分析、提出建议，还是可以直接执行设备操作。
- 设备重启接口对每类硬件的实际支持范围。

这些问题应在对应功能开始实现前单独确认，不应在当前产品骨架阶段凭空假设。
